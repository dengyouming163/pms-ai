# ADR 0002：写操作先审批，执行层再做硬校验

- 日期：2026-11-21
- 状态：已采纳

## 背景

收益管理子图会真正修改 `pms_bui_pricing_calendar` 的房价。这是本项目与纯问答 Demo 的分水岭：Agent 必须能写，但一旦写错就是真金白银的损失。审批界面由人操作，而人可能误点、请求可能被伪造或重放，因此"人批准了"不能作为唯一的安全依据。

## 选项

1. **只做审批**：实现简单，但审批请求本身是不可信输入，越权/篡改无法拦截。
2. **只做服务端硬校验**：无需人工，但价格策略属于业务判断，机器无法独立承担。
3. **审批 + 执行层硬校验**：审批决定"做不做"，硬校验决定"能不能做"。

## 决定

采用方案 3，写操作固定五步：

1. 子图生成 `Proposal`（tool / params / before / after / reason / evidence_refs / idempotency_key）；
2. `interrupt()` 挂起，checkpoint 持久化，运行进入 `awaiting_approval`；
3. 协作台展示前后差异、理由与证据，人批准或驳回（驳回必填理由）；
4. `POST /runs/{id}/approve` 从断点恢复；
5. `revenue_execute` 重新校验：租户归属、价格硬边界（±30%）、不等于当前价、目标资源仍存在、同一审批不得重复执行。

审批结果写入 `agent_approvals`，业务变更由 `pms-server` 的 `/price-adjust` 落库并返回前后快照，两边可对照审计。

## 后果

- 审批通过但校验失败时，run 终止为 `guard_rejected`，不会产生写入；这是刻意的冗余。
- 执行层是最后一道闸，因此即使前端或 Agent 被提示词注入，也无法越过 ±30% 与租户边界。
- 已知债务：`idempotency_key` 目前只保存在审批单快照中，尚未落唯一索引做跨进程去重；生产化时应补数据库唯一约束。审批接口本身也还未接入用户身份鉴权，当前依赖内部网络与商户白名单收敛。
