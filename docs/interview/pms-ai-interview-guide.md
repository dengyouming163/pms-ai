## 1. 一分钟项目速览（STAR）

**Situation（背景）**
我做过一套真实在用的民宿 PMS：商家后台、员工移动端、业务 API 和一套 CrewAI 写的 AI 服务。业务是真的，但 AI 那一层不可观测、不可评测、写操作没有审批，本质上还是「提示词套 HTTP 接口」。它只能演示，不能叫生产级。

**Task（任务）**
我要把它改造成一个能公开演示、能被追问、能被复现的多智能体协作平台，用来证明我具备 AI 应用与 Agent 工程的完整能力。

**Action（行动）**
1. 把 CrewAI 换成 LangGraph，采用 Supervisor + 四个领域子图的拓扑：收益管理、晨报诊断、住中客服、渠道体检。
2. 自研事件回调，把每一次运行拆成可回放的时间轴；前端做三栏协作台，能实时看、也能倒带看。
3. 写操作全部走「提案 → interrupt 挂起 → 人审批 → 执行层硬校验」四步，审批后还要再校验租户、价格边界和幂等键。
4. 做双模运行时：默认回放已录制的模型响应，无 key 也能完整演示；配 key 后切真实模型，产出真实 LangSmith 链路。
5. 建 30 条评测用例，锁定基线，指标含路由准确率、工具选择 F1、任务成功率、越权拦截率、P95 延迟，回归用 0/1/2 三种退出码。

**Result（结果）**
- 陌生人 clone 后一条命令跑通「Agent 改真实房价」的全流程。
- 越权调用、超边界调价、重复幂等键三类攻击 100% 拦截，且都有审计记录。
- 面试时任何一个「怎么保证」的问题，都能落到代码、表结构或报告上。

## 2. 专业词汇表

### 2.1 业务域

| 词汇 | 英文 / 缩写 | 含义 | 在本项目中的位置 |
|---|---|---|---|
| PMS | Property Management System | 物业/酒店管理系统，管房态、订单、价格、渠道、账务 | 整个项目底座 |
| 房态 | Room Status | 房间当前状态：空闲、在住、脏房、维修 | `ops` 子图的体检对象 |
| 入住率 | Occupancy Rate / OCC | 已售房间数 ÷ 可售房间数 | 调价的核心输入 |
| 平均房价 | ADR（Average Daily Rate） | 客房总收入 ÷ 已售房间数 | 与 RevPAR 一起看 |

| 收益管理 | Revenue Management / RMS | 用价格与库存调节供需，最大化 RevPAR | `revenue` 子图的业务目标 |
| 价格日历 | Rate Calendar | 按日期 × 房型维护的价格表 | 写操作的落点 |
| 竞对价 | Competitor Rate | 同区域同档位酒店的可比价格 | 调价的外部锚点 |
| 渠道 | Channel / OTA | 携程、美团、飞猪等分销渠道 | 佣金与价差的来源 |
| 佣金率 | Commission Rate | 渠道按成交额抽取的比例 | 净价测算的关键参数 |
| 直连 | Direct Connect | PMS 与 OTA 之间的库存/价格同步接口 | `ota` 子图检查对象 |
| 超时未确认 | Timeout Unconfirmed | 渠道订单在规定时间内未确认，可能被取消 | 晨报中的风险项 |
| 脏房 | Dirty Room | 退房后待清洁的房间 | 房务调度的输入 |
| 建筑决策记录 | ADR（Architecture Decision Record） | 记录架构选择的背景、选项与后果 | `docs/adr/`，注意与平均房价同名不同义 |

> 面试提醒：ADR 在酒店语境是平均房价，在工程语境是架构决策记录。同一个缩写，回答前先确认对方问的是哪个。

### 2.2 AI / Agent

| 词汇 | 英文 | 含义 | 为什么重要 |
|---|---|---|---|
| 大语言模型 | LLM | 基于 Transformer 的概率生成模型 | 一切能力的底座 |
| 提示词 | Prompt | 给模型的指令与上下文 | 决定行为边界的第一层 |
| 工具调用 | Function Calling / Tool Calling | 模型输出结构化调用意图，由运行时执行并把结果回灌 | Agent 与聊天机器人的分水岭 |
| 智能体 | Agent | 具备「感知 → 决策 → 行动 → 观察」循环的系统 | 本项目的核心形态 |
| 多智能体系统 | MAS, Multi-Agent System | 多个具备独立职责的 Agent 协作完成目标 | Supervisor + 子图 |
| 编排 | Orchestration | 决定谁在什么时候做什么 | LangGraph 的职责 |
| 监督者 | Supervisor | 只做路由与汇总的中心节点，不持有业务工具 | 本项目的顶层设计 |

| 状态图 | StateGraph | 以共享状态为中心、节点为函数、边为转移的图 | LangGraph 的核心抽象 |
| 归约器 | Reducer | 定义多个节点写同一字段时如何合并（如追加消息） | `add_messages` |

| 线程 | Thread | 一次会话/运行的持久化标识，checkpoint 按 thread 存 | `thread_id` |

| 幂等 | Idempotency | 同一请求执行多次，效果与执行一次相同 | 防止重复调价 |

| 温度 | Temperature | 采样随机性参数，越低越确定 | 结构化输出用低温度 |
| 检索增强生成 | RAG | 先检索资料再让模型基于资料回答 | `guest` 子图复用知识库 |
| 嵌入 | Embedding | 把文本映射为向量，用于语义检索 | 知识库底座 |

## 3. 基础知识解析

### 3.1 LLM 应用的三个层次

| 层次 | 形态 | 能力 | 局限 | 本项目 |
|---|---|---|---|---|
| L1 提示词 | 单轮问答 | 上手最快 | 无外部事实、无行动能力 | 各节点内的指令 |
| L2 检索增强 | RAG | 有事实依据 | 只能回答，不能改变系统 | `guest` 子图 |
| L3 智能体 | Tool + Planning + Memory | 能读能写、多步推理 | 需要护栏、评测、可观测 | 整体架构 |

面试时先讲清这三层，再说明本项目在 L3，且刻意保留 L2 作为知识来源，避免「什么都让模型记」。

### 3.2 工具调用的完整生命周期

1. **声明**：用 JSON Schema 描述工具名、参数、必填项、取值范围。
2. **绑定**：把 schema 交给模型（`bind_tools`），模型据此生成调用意图。
3. **决策**：模型输出「调用哪个工具、传什么参数」或「直接回答」。
4. **校验**：运行时用 Pydantic 校验参数，不合法直接驳回给模型重试。
5. **执行**：真正调用外部系统，捕获异常与超时。
6. **回灌**：把结果作为一条工具消息写回消息列表，进入下一轮。
7. **终止**：模型不再调用工具，或达到步数/预算上限。

**关键认知**：模型不执行任何代码，它只产出结构化意图。真正的权限控制在第 4、5 步，所以「工具白名单」必须落在运行时而不是提示词里。

### 3.3 多智能体拓扑的三种形态

| 拓扑 | 结构 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| Supervisor | 中心路由 + 领域子图 | 路径可控、可评测、可回放 | 路由本身要评 | 生产系统（本项目） |
| Plan-and-Execute | 先规划 DAG 再执行 | 跨领域任务强 | Planner 失败即全盘失败 | 研究型任务 |
| Swarm / Handoff | Agent 间直接交接 | 灵活、叙事强 | 不可预测、难终止、难评测 | Demo、探索 |

**为什么本项目选 Supervisor**：酒店业务需要「可解释的确定性」。老板问「为什么降了 30 块」，系统必须能回答是哪条证据、哪个工具、哪一步推理。Swarm 给不了这个。

### 3.4 LangGraph 的五个核心概念

| 概念 | 作用 | 类比 |
|---|---|---|
| State | 全局共享的、有类型的数据结构 | 函数式编程里的累加器 |
| Node | 一个纯函数：读 State，返回增量更新 | 流水线上的工位 |
| Edge | 固定转移 | 传送带 |
| Conditional Edge | 按状态决定下一步 | 分拣机 |
| Checkpointer | 每步状态快照，按 thread 持久化 | 游戏存档 |

**中断与恢复**：节点内调用 `interrupt(payload)` 会挂起图，把当前状态写入 checkpoint。外部用 `Command(resume=decision)` 恢复，图从断点继续。这是人审不需要自己写状态机的根本原因。

**为什么比手写状态机好**：手写要实现「状态序列化、断点恢复、并发安全、事件发射」四件事；LangGraph 把前三件做掉了，你只需要关心业务节点。

### 3.5 人审（HITL）的正确姿势

常见错误做法：模型说「我要改价」，后端直接执行，然后记一条日志。

正确做法分四层：

1. **提案与执行分离**：模型只能生成提案，不能直接调用写工具。
2. **挂起而非阻塞**：运行暂停并落库，不占用进程等待，人可能一小时后才审批。
3. **审批后硬校验**：执行层重新校验租户、边界、幂等。审批界面是外部输入，不可信。
4. **全链路审计**：谁、何时、基于什么证据、改了什么、结果如何。

### 3.6 评测的三个层次

| 层次 | 做法 | 成本 | 能发现什么 |
|---|---|---|---|
| 单元 | 每个节点/工具独立测 | 低 | 参数校验、边界条件 |
| 图级 | 固定输入跑整条图，断言路径与输出 | 中 | 路由、工具选择、步数 |
| 端到端 | 真实前端 + 真实模型 | 高 | 集成缺陷、体验问题 |

**本项目策略**：图级评测用回放保证确定性，作为 CI 门禁；端到端只在发版前人工跑一次。

### 3.7 可观测的三个问题

- **发生了什么**：事件流水（谁调了什么、耗时多少、成功失败）。
- **为什么这样**：证据链（模型基于哪条数据做的决定）。
- **花了多少钱**：token 与成本按运行、按租户聚合。

只做第一层的系统，出问题时只能看日志猜；三层都做，才能定位「是召回错了、还是模型选错了工具、还是工具本身失败」。

### 3.8 成本与延迟

| 手段 | 效果 | 代价 |
|---|---|---|
| 预算上限（步数/token/时间） | 防止单次运行失控 | 复杂任务可能被截断 |
| 模型分级 | 路由用小模型、推理用大模型 | 多一套配置 |
| 工具结果缓存 | 同一运行内不重复拉取 | 需处理数据新鲜度 |
| 并行子节点 | 晨报四路体检并行 | 需要并发安全的状态合并 |
| 流式输出 | 感知延迟下降 | 实现复杂度上升 |
| 回放模式 | 演示与评测零成本 | 不代表真实模型表现 |

## 4. 项目类面试题

### Q1：请用一句话介绍这个项目。

一个把真实民宿 PMS 改造成多智能体协作平台的项目：Agent 能读真实的房态、订单、竞对价，提出调价建议，经人审批后真正改写价格日历，并且每一次运行都能回放、能评测、能归因。

### Q2：为什么要重构原来的 AI 服务？它已经能跑了。

能跑和能信是两件事。原实现有三个硬伤：

- **不可观测**：CrewAI 内部怎么决策、调了哪些工具，只能看日志。
- **不可评测**：没有固定用例和基线，改一次提示词不知道变好还是变坏。
- **不可控**：写操作没有审批与硬校验，理论上模型可以直接改价格。

对商家来说，一个会自己改价的 AI 比没有 AI 更可怕。所以重构的核心不是「换框架」，是补齐生产级的三件事：可观测、可评测、可控制。

### Q3：为什么从 CrewAI 换成 LangGraph？

| 维度 | CrewAI | LangGraph |
|---|---|---|
| 抽象 | 角色 + 任务 + 流程 | 状态 + 节点 + 边 |
| 控制力 | 流程由框架调度，细节黑盒 | 每一步都是你的代码 |
| 状态持久化 | 无原生 checkpointer | 原生支持，按 thread 存 |
| 中断恢复 | 需自己实现 | 原生 `interrupt` / `resume` |
| 可测试性 | 整条 Crew 一起测 | 节点、子图可单独测 |
| 上手速度 | 快 | 慢一些 |

CrewAI 适合「先跑起来」，LangGraph 适合「跑得可控」。我这个项目要讲人审、回放、评测，这三件事都依赖状态可控，所以换。

**追问：换框架的代价是什么？**
重写编排层，约 8 个 Crew 的逻辑要拆成节点；团队要重新熟悉 API；LangGraph 版本迭代快，需要锁版本并隔离适配层。

### Q4：为什么是 Supervisor，不是 Swarm？

因为要可评测。Swarm 的路径由 Agent 之间自由交接决定，同一输入两次运行可能走不同路径，基线无法锁定。Supervisor 的路由是单点、可断言、可回放，评测才有意义。

而且业务上也需要一个「总台」：老板问的是「明天要不要涨价」，不是「请让收益 Agent 和房务 Agent 自行商量」。

### Q5：四个子图为什么这样切？

按**决策类型**切，不按部门切：

- `revenue`：需要外部锚点（竞对价）+ 内部数据（入住率）+ 写操作。深度主线。
- `ops`：只读、多路并行、输出是报告。广度展示。
- `guest`：只读、依赖知识检索、对话形态。
- `ota`：只读为主、规则明确、异常检测。

这样切的好处是每个子图的工具集互不重叠，权限边界天然清晰，评测也能分开做。

### Q6：项目里最难的技术点是什么？

**审批后的一致性**。人审批时看到的价格和实际执行时的价格可能已经变了（别人改过、房型下架、租户切换）。所以执行层必须重新校验：

- 租户归属是否仍然匹配
- 目标房型与日期是否仍存在
- 变更幅度是否仍在 ±30% 内
- 幂等键是否已被使用
- 当前价格是否与提案时的 `before` 一致（乐观并发）

任何一项不通过就终止，并把失败原因写回事件流。这块不是模型问题，是分布式系统问题。

### Q7：为什么审批之后还要再校验一次？不是多此一举吗？

不多余，是刻意的纵深防御。审批请求来自前端，前端可以被篡改、可以被重放、可能因为页面停留过久而基于过期数据。执行层是最后一道闸，它只信数据库当前状态，不信上游传来的任何结论。

代价只有几条查询，收益是把「越权改价」这类事故的概率压到接近零。

### Q8：Agent 会不会编造数据？

设计上禁止。约束有三条：

1. 最终回答里的每个数字必须能追溯到某条 `evidence`，否则合成节点会剥离并标注「无数据支撑」。
2. 工具失败重试一次后返回错误证据，Agent 必须说「数据不可用」，而不是估算。
3. 评测用例里专门有「缺数据」和「工具报错」两类，用来验证它确实会承认不知道。

### Q9：没有 API key 怎么演示？

双模运行时。真实调用时把「模型 + 提示词哈希 + 响应」录成夹具，回放模式按哈希命中直接返回。评测和离线演示都跑回放，结果完全确定。

**关键设计**：回放未命中直接报错，不回落真实模型。否则夹具缺失会被随机输出掩盖，评测数据就被污染了。

### Q10：这个项目和你另外两个项目什么关系？

- `rag-knowledge-base` 解决「知识找得准、敢拒答」，是知识底座。
- `enterprise-agent-platform` 解决「通用工具调用、人审、计量」，是横向平台。
- 本项目是纵向业务纵深：真实行业数据、真实写操作、真实收益归因。

三者不共享代码、不共享数据库，只共享方法论。面试时可以形成「底座 → 平台 → 应用」的完整叙事。

### Q11：如果让你再做一遍，会改什么？

两件事：

1. **更早做评测**。先写 5 条用例再写图，比写完图再补用例省一半时间。
2. **把工具契约单独成包**。现在工具的参数定义在 Python 侧，前端展示时又要写一遍 TypeScript 类型，容易漂移。

### Q12：这个项目上线过吗？有多少用户？

要诚实：业务系统在生产环境跑过，但这套 Agent 改造是面向作品集的重构，用虚构品牌和种子数据演示。我不把「设计完成」说成「线上验证」，这是两回事。

**追问：那怎么证明它能用？**
用三层证据：离线评测报告（30 条用例、八项指标）、安全演练（三类越权攻击全部拦截）、可回放的真实链路（配 key 跑一遍并录屏）。

## 5. 架构类面试题

### Q13：为什么 Agent 服务不直连数据库？

三个原因：

1. **权限边界**。直连意味着 Agent 能看到整张表，工具白名单就形同虚设。走 API 才能按端点授权。
2. **可审计**。所有写操作都经过同一层，审计点唯一。
3. **可替换**。业务表结构变化时，只需要改工具适配层，Agent 不用动。

代价是多一跳网络开销。对 Agent 场景（单次运行秒级），这点开销可以忽略。

### Q14：为什么要单独建 `agent` schema，不复用现有的 AI 表？

现有 `pms_bui_ai_*` 表是线上历史资产，字段语义与新的运行模型对不上（比如没有事件序、没有审批快照）。硬复用会带来两个问题：迁移受制于历史数据、新逻辑被旧字段绑死。

新 schema 的好处是：可以自由演进、可以整库清空重来、可以让评测数据与生产数据物理隔离。

### Q15：为什么用 SSE 而不是 WebSocket？

事件流是**单向**的（服务端 → 前端），SSE 足够，而且：

- 基于普通 HTTP，不需要额外的协议升级与心跳设计。
- 断线重连是浏览器原生行为，配合 `Last-Event-ID` 可以从断点续传。
- 更容易穿透代理与企业网络。

WebSocket 的优势是双向低延迟，本项目不需要前端向 Agent 实时发指令（审批走普通 POST）。

### Q16：断线重连后怎么保证事件不丢不乱？

- 每条事件有单调递增的 `seq`，同时落库。
- 前端记录已收到的最大 `seq`，重连时带上 `Last-Event-ID`。
- 服务端从该 `seq` 之后继续推送；如果内存缓冲已淘汰，就从 `agent_events` 表回查。

**本质**：事件表是唯一事实来源，SSE 只是传输通道。通道可以断，事实不能丢。

### Q17：三个服务的链路怎么串起来排查问题？

`trace_id` 由前端生成，放在请求头里，经 Agent 透传到业务服务。三端日志都打这个 ID，出问题时按 ID 聚合即可看到完整链路：前端请求 → Agent 路由 → 工具调用 → SQL。

这比「按时间戳猜」可靠得多，尤其是在并发场景。

### Q18：为什么保留扁平目录，不做 monorepo？

四个子项目各自有独立的构建体系（pnpm workspace / pyproject），挪进 `apps/` 只增加路径改动风险，不产生实际收益。真正的工程感体现在 `eval/`、`deploy/`、`docs/`，而不是目录嵌套。

**追问：那怎么保证依赖一致？**
各自锁版本；CI 里对四个模块分别跑构建与测试；根目录只放编排脚本与文档。

### Q19：一键启动是怎么做到的？

`docker compose up` 拉起五个容器：PostgreSQL、Redis、业务 API、Agent 服务、前端。启动顺序由 healthcheck 保证：数据库先 ready，业务服务再做迁移与种子灌入，Agent 最后启动。

前端容器内置了「等待后端健康」的启动脚本，避免用户看到白屏。

### Q20：多租户隔离怎么做？

三层：

1. **状态层**：`AgentState.tenant` 固定携带 merchant/store/user，所有工具调用都带这三个值。
2. **服务层**：业务 API 用 `tenantWhere` 强制拼租户条件，Agent 无法构造跨租户查询。
3. **执行层**：审批后的写操作再次校验目标资源是否属于当前租户。

**为什么不在 Agent 层做**：Agent 可能被注入、可能出错；隔离必须落在数据访问层。

### Q21：怎么做灰度与回滚？

- **模型灰度**：模型配置走环境变量 + 运行时开关，可按子图切换。
- **子图灰度**：每个子图有独立开关，关掉后 Supervisor 路由到降级分支。
- **版本回滚**：镜像打 tag，compose 指定版本即可回退。
- **数据回滚**：`agent` schema 与业务表分离，最坏情况可以整 schema 重建，不影响业务数据。

### Q22：怎么防止密钥进仓库？

三道：`.gitignore` 白名单（只放行 `.env.example`）；提交前脚本扫描常见密钥模式（`sk-`、`AKID`、私钥头）；CI 再扫一遍，命中即失败。

### Q23：测试策略是什么？

| 层级 | 对象 | 工具 | 是否进 CI |
|---|---|---|---|
| 单元 | 工具参数校验、护栏函数、状态归约 | pytest | 是 |
| 图级 | 固定输入跑子图，断言路径与输出 | pytest + 回放 | 是 |
| 契约 | Agent 与业务 API 的接口字段 | 契约测试 | 是 |
| 端到端 | 完整演示路径 | 脚本 + 浏览器 | 发版前 |

### Q24：如果 Agent 服务挂了，业务系统还能用吗？

能。Agent 是旁路增强，不是主链路。业务后台的房态、订单、价格管理都不依赖 Agent；协作台会显示「Agent 服务不可用」，但不影响商家正常操作。

**设计原则**：AI 故障不能升级为业务故障。

## 6. AI / Agent 类面试题

### Q25：Agent 和「带工具调用的聊天机器人」有什么区别？

聊天机器人是「一问一答 + 可选工具」；Agent 是「给定目标，自主决定步骤、调用工具、观察结果、调整计划，直到完成或放弃」。

三个判定标准：

1. 是否需要多步决策（不是一次调用能解决）。
2. 是否需要根据中间结果改变策略。
3. 是否需要对外部系统产生副作用（写操作）。

本项目三条都满足。

### Q26：多智能体的失败模式有哪些？

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 路由错误 | 该找收益却找了房务 | 路由评测 + 兜底分支 |
| 死循环 | 反复调同一个工具 | 步数上限 + 重复调用检测 |
| 上下文膨胀 | 工具返回太大，挤爆窗口 | 结果摘要 + 引用而非全文 |
| 责任稀释 | 每个 Agent 都以为别人会做 | Supervisor 显式汇总与校验 |
| 成本爆炸 | 并行子图各自狂调模型 | 全局预算 + 单节点预算 |
| 错误传播 | 上游错误数据被下游当事实 | 证据链 + 数据可用性标记 |

### Q27：怎么防止 Agent 乱改价格？

四层防线：

1. **工具层**：写工具不在 Supervisor 手里，只在 `revenue` 子图，且只能通过审批节点触发。
2. **提案层**：模型只能生成 `Proposal`，包含前后值、理由、证据、幂等键。
3. **审批层**：`interrupt` 挂起，人工批准或驳回。
4. **执行层**：重新校验租户、±30% 边界、幂等键、当前值是否仍与提案一致。

另外所有变更都有审计记录，可追溯到具体的人与证据。

### Q28：为什么价格边界是 ±30%？

这是业务约束，不是技术限制。超过 30% 的调价通常意味着数据异常（竞对价抓错、房型配置错），而不是真实的市场信号。硬边界的作用是拦住「模型基于错误数据做出剧烈调整」。

边界值放在执行层，不放在提示词里——提示词可以被绕过，代码不能。

### Q29：LangGraph 的 checkpointer 解决什么问题？

三个：

- **断点续跑**：人审可能几小时后才处理，进程不能一直等着。
- **故障恢复**：服务重启后能从最后一步继续。
- **回放与调试**：每一步的状态都可查，能精确复现当时的决策上下文。

**追问：checkpoint 存哪？**
PostgreSQL 的 `agent` schema，与业务数据物理隔离但同库，省一套运维。

### Q30：interrupt 和「把任务存数据库等定时轮询」有什么区别？

本质都是挂起，区别在**状态归属**：

- 自己实现：你要序列化整个图的状态、设计恢复协议、处理并发与版本兼容。
- `interrupt`：框架帮你存，恢复时从断点继续，你只关心业务决策。

自己实现不是不行，但容易在「恢复后状态不一致」上踩坑。

### Q31：怎么做评测才不是自欺欺人？

四条纪律：

1. **用例先于实现**：先写期望路径，再写代码，避免「按实现写断言」。
2. **回放保证确定性**：同一用例跑两次结果必须一致，否则指标没有意义。
3. **基线锁定**：基线文件不改，新增用例另建文件，避免分母漂移。
4. **区分退化与漂移**：指标变差是退化（退出码 1），模型或夹具变了是漂移（退出码 2），两者排查方向完全不同。

### Q32：路由准确率怎么算？为什么单独评它？

```
路由准确率 = 路由到正确子图的运行数 ÷ 总运行数
```

单独评是因为它是**所有下游指标的前提**：路由错了，后面工具选得再对也没用。而且它是最容易被提示词改动影响的一环，需要独立监控。

### Q33：工具选择用 F1 而不是准确率，为什么？

因为工具选择是**集合匹配**问题：一次运行可能该调 3 个工具，实际调了 2 个（漏）或 4 个（多）。

- 准确率只回答「调了的里面有多少是对的」，漏调不惩罚。
- F1 同时惩罚漏调和多调，更贴近真实质量。

### Q34：P95 延迟为什么用回放测？

回放排除了模型网络抖动，测的是**系统自身开销**（图调度、工具调用、序列化）。真实模型的延迟方差太大，混在一起无法判断是架构问题还是供应商问题。

真实链路的延迟单独用 `--live` 跑一组，作为参考值而非门禁值。

### Q35：成本怎么控？

| 层级 | 手段 |
|---|---|
| 单次运行 | 12 步、8 万 token、90 秒硬上限 |
| 子图 | 每个子图独立预算，防止一个子图吃掉全部 |
| 模型 | 路由用小模型，深度推理用大模型 |
| 工具 | 同一次运行内缓存重复查询 |
| 演示 | 默认回放，零成本 |
| 监控 | 按运行、按租户聚合 token 与金额，异常告警 |

### Q36：怎么处理工具超时？

- 单工具超时 10 秒，重试 1 次。
- 仍失败则把错误写入证据，标记该数据源不可用。
- Agent 必须显式说明「某项数据不可用」，不得用其他数据替代估算。
- 如果关键数据（如当前价格）不可用，直接终止，不产出建议。

**原则**：宁可不说，不可乱说。

### Q37：怎么防提示词注入？

注入的本质是「外部内容被当成了指令」。防线：

1. 工具返回的内容永远标记为**数据**，不拼进系统指令区。
2. 工具白名单在运行时生效，模型被诱导也调不到未授权工具。
3. 写操作必须过人审，注入无法直接造成副作用。
4. 输出做数值溯源，编造的数字会被剥离。

### Q38：为什么不做微调？

- 数据量不够：真实调价决策样本只有几百条，微调容易过拟合。
- 变更太快：业务规则一个月一变，微调跟不上。
- 可解释性：面试和客户都需要知道「为什么这么建议」，微调给不了解释。

现阶段「提示词 + 工具 + 证据链」的性价比最高。

### Q39：Agent 的记忆怎么做？

分三类，本项目只做前两类：

| 类型 | 内容 | 存储 | 本期 |
|---|---|---|---|
| 短期 | 本次运行的消息与证据 | State + checkpoint | 做 |
| 长期偏好 | 商家偏好（如「周末不低于 600」） | `agent_memories` 表 | 做（轻量） |
| 语义记忆 | 历史案例的向量检索 | 向量库 | 不做，避免与知识库项目重复 |

长期记忆的写入必须是**显式**的（审批通过后写入），不能让模型自己决定记什么，否则会累积错误偏好。

### Q40：为什么默认回放而不是默认真实模型？

三个理由：

1. **可复现**：面试官 clone 后不需要申请 key，也不会因为模型版本变化看到不同结果。
2. **零成本**：评测跑 30 条用例，真实调用要花钱，回放免费。
3. **确定性**：同一用例两次运行结果一致，指标才有意义。

真实链路用 `--live` 单独验证，两条路都保留。

### Q41：如果 LangGraph 明天不维护了怎么办？

架构上做了隔离：图定义在 `app/graph/`，业务节点是普通 Python 函数，持久化通过 `persistence/` 适配层。真要换框架，重写的是图定义与适配层，业务逻辑可以复用。

这也是为什么节点里不直接调用 LangGraph API 的原因。

### Q42：多 Agent 并行时状态怎么合并？

- 只读的并行节点（如晨报四路体检）各自写自己的证据列表，用追加型 reducer 合并。
- 写操作绝不允许并行，必须串行经过审批。
- 共享的可变字段（如预算计数）用原子累加，避免覆盖。

**原则**：并行只用于读，写永远串行。

### Q43：怎么判断一次运行「成功」？

三个条件同时满足：

1. 达成目标（如产出了可执行的调价建议）。
2. 未触发红线（无越权、无超边界、无预算超限）。
3. 输出可追溯（每个关键数字都有证据）。

只看「有没有返回文本」是不够的——模型最容易在失败时编一段看起来合理的话。

### Q44：如果模型坚持给出错误建议，系统能拦住吗？

能拦一部分，不能全拦：

- 能拦：超边界、越权、无证据的写操作、数据缺失时的臆测。
- 不能拦：在允许范围内但业务上不合理的建议（如淡季涨价 5%）。

后者需要人工判断，这正是审批存在的意义。系统的责任是「把错误变得可发现」，不是「保证永远正确」。

### Q45：你在这个项目里最想被问的问题是什么？

「你怎么证明它靠谱？」

因为我可以给出三样东西：锁定的评测基线、三类攻击的拦截记录、可回放的真实链路。很多 Agent Demo 只能演示成功路径，我能演示失败路径和拒绝路径。

## 7. 业务与产品类面试题

### Q46：为什么选民宿/酒店这个场景？

三个原因：

1. **数据天然结构化**：房态、订单、价格、渠道都有明确字段，不需要从零造数据。
2. **决策有明确指标**：RevPAR、入住率、ADR，好坏可量化，收益归因能落地。
3. **写操作有真实风险**：改价直接影响收入，天然适合讲审批与护栏。

比「智能客服」更能体现工程深度。

### Q47：商家为什么需要一个 AI 收益经理？

中小民宿老板通常没有专职收益管理岗，定价靠经验和隔壁看一眼。AI 能做到三件人做不到的事：

- 每天扫描全部房型 × 未来 90 天的价格机会。
- 同时对比多个竞对与渠道净价。
- 把决策依据写清楚，老板只需要点「批准」。

### Q48：怎么衡量 AI 带来的收益？

`agent_insights` 表记录每条被采纳建议的：

- 基线收入（不调价的预测值）
- 实际收入（采纳后观察窗口内的真实值）
- 归因说明（同期竞对、节假日、渠道变化）

用「采纳组 vs 未采纳组」的对比做归因，而不是简单说「涨了多少」。

### Q49：如果商家不信任 AI 怎么办？

产品上做了三件事：

- 建议必须附证据（竞对价截图、入住率曲线），不是一句「建议涨价」。
- 分级执行：小幅度自动、中幅度审批、大幅度双人确认。
- 可回滚：每次改价都有前后值，一键恢复。

信任是靠「可解释 + 可撤销」建立的，不是靠模型更聪明。

### Q50：这个项目如果商业化，下一步做什么？

按优先级：

1. 接真实 OTA 直连，让价格真正同步到渠道。
2. 做多门店对比与集团视图。
3. 收益归因做成报表，按周推送。
4. 模型成本转嫁：按调用量计费或打包进订阅。

但这些都是后话，当前阶段的目标是把「可信」做扎实。

## 8. 压力追问与反例

### Q51：「这不就是调了几个 API 吗？」

表面是，实质不是。调 API 是工具层，真正的工作在四件事：

- 决定**什么时候**调、调哪个（路由与规划）。
- 决定**调完之后**怎么办（观察与调整）。
- 保证**不该调的调不到**（权限与护栏）。
- 证明**整体是变好了**（评测与基线）。

任何一条缺失，系统就退化成脚本。

### Q52：「你说的可观测，不就是打日志吗？」

日志是文本，不可结构化查询；可观测是结构化事件：

- 每条事件有 `run_id`、`seq`、`node`、`type`、耗时、token。
- 可以按运行聚合、按节点统计、按类型过滤。
- 前端能据此画出时间轴，评测能据此断言路径。

日志回答「发生了什么」，事件模型回答「为什么这样、花了多少」。

### Q53：「回放是不是作弊？」

不是。回放验证的是**编排与工具链路的正确性**，不是模型能力。这两件事必须分开评：

- 回放跑不通，说明图、工具、状态管理有 bug。
- 回放跑通了但真实模型效果差，说明提示词或模型选型有问题。

混在一起测，出问题无法定位。

### Q54：「审批是不是把责任推给人？」

不是。审批是**责任边界**的设计：

- 系统负责「把决策所需的信息完整呈现」，并对越界行为兜底。
- 人负责「业务判断」，因为他掌握系统不知道的上下文（如明天有政府接待）。

完全自动的定价系统在中小商家场景不现实，也不该由技术单方面决定。

### Q55：「四个子图是不是太多了？」

如果只做调价，一个子图就够。但作品集要展示的是**协作**：Supervisor 如何在多个领域之间路由与汇总。四个是最小可演示的广度，再少就看不出协作，再多就摊薄深度。

砍单线也说明了：M2 的 `guest` 和 `ota` 可以降级为只读体检，`revenue` 不动。

### Q56：「你这些指标是自己定的吧，有什么意义？」

指标分两类：

- **绝对门槛**（越权拦截 100%、审批正确 100%）：安全类指标没有妥协空间。
- **相对基线**（成功率、步数、成本）：用于回归对比，绝对值不重要，趋势重要。

我不会声称「90% 成功率」是行业标准，我只说「这是本项目的基线，改动不能让它变差」。

### Q57：「如果模型 API 涨价 10 倍怎么办？」

系统已做的准备：

- 模型通过 OpenAI 兼容层接入，可切换供应商。
- 路由与简单节点可以用小模型。
- 工具结果缓存减少重复调用。
- 回放模式保证演示与评测不受影响。

真要涨价，先降级模型分级，再考虑压缩上下文与步数。

### Q58：「这个项目你一个人做的？」

是。业务系统是过去工作的积累，Agent 改造、评测、协作台是本轮独立完成。我会明确区分「继承的资产」和「本轮的工作」，不把前人的东西算成自己的。

## 9. 现场演示脚本（5 分钟口述版）

| 时间 | 动作 | 要讲的话 |
|---|---|---|
| 0:00 | 打开后台首页 | 「这是一套真实业务的民宿 PMS，今天青岩店入住率 82%。」 |
| 0:30 | 进入协作台，输入「明天要不要涨价？」 | 「注意我只给了一个自然语言目标，没有指定用哪个 Agent。」 |
| 1:00 | 观察 Supervisor 分派 | 「顶层只做路由，它自己没有任何业务工具，所以不会绕过子图乱来。」 |
| 1:30 | 工具调用逐张出现 | 「每次调用都有参数、耗时、返回摘要，这是我自研的事件回调，不是框架日志。」 |
| 2:30 | 收到 L2 调价提案 | 「它没有直接改价，而是生成了提案：当前 480、建议 520、理由是同区域竞对满房。」 |
| 3:00 | 点开证据 | 「每条结论都能点回原始数据，这是防止编造的最后一道。」 |
| 3:30 | 批准 | 「批准之后执行层还会再校验一次租户、±30% 边界和幂等键。」 |
| 4:00 | 回到价格日历 | 「价格真的变了。再看收益归因面板，这条建议被记进了采纳记录。」 |
| 4:30 | 打开评测报告 | 「30 条用例、八项指标、基线对比。越权拦截 100%。」 |
| 4:50 | 打开回放页面 | 「任何一次历史运行都能倒带重看，包括失败和拒绝的路径。」 |

**演示禁忌**：不要只演示成功路径；主动展示一次「工具数据缺失 → Agent 明确说不知道」和一次「审批驳回」，可信度会高很多。

## 11. 附录：指标口径与计算公式

| 指标 | 公式 | 说明 |
|---|---|---|
| 路由准确率 | 正确子图运行数 ÷ 总运行数 | 单标签分类 |
| 工具选择精确率 | 交集数 ÷ 实际调用数 | 惩罚多调 |
| 工具选择召回率 | 交集数 ÷ 期望调用数 | 惩罚漏调 |
| 工具选择 F1 | 2PR ÷ (P + R) | 综合 |
| 任务成功率 | 达成目标且无红线 ÷ 总运行数 | 红线含越权、超预算、无证据 |
| 平均步数 | 节点执行总数 ÷ 运行数 | 衡量效率 |
| 单任务成本 | Σ(token × 单价) ÷ 运行数 | 按模型分别计价 |
| 越权拦截率 | 成功拦截数 ÷ 应拦截数 | 必须 100% |
| 审批正确率 | 正确审批结论数 ÷ 审批总数 | 应批的批、应拒的拒 |
| P95 延迟 | 第 95 百分位端到端耗时 | 回放口径 |
| 采纳率 | 被采纳建议数 ÷ 建议总数 | 产品指标 |
| 归因增益 | Σ(采纳后收入 − 基线预测收入) | 需控制同期变量 |

**评测退出码**

| 码 | 含义 | 处理 |
|---|---|---|
| 0 | 全部达标 | 允许合并 |
| 1 | 指标退化超阈值 | 阻断合并，定位退化点 |
| 2 | 条件漂移无法比较 | 重建基线并说明原因 |

## 附：如何在面试中组织回答

**三段式**：先说结论 → 再说理由（不超过三条）→ 最后给证据（代码位置 / 表结构 / 报告数字）。

**不要在没实现的地方用完成时**。「我设计了」和「我实现了」要分清，被追问到细节时，诚实比圆场得分高。

**准备三个失败故事**：一次路由错误、一次工具超时、一次审批驳回。讲清楚怎么发现、怎么定位、怎么修，比讲十个成功案例更有说服力。
